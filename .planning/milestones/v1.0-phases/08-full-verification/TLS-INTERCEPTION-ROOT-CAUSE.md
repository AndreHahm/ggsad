# Root Cause Analysis — `uv sync --locked` `UnknownIssuer` Failure

## Record

- Analyst: Claude Code
- Date: 2026-08-21
- Scope: Read-only diagnosis. No repository or system files were modified.
- Trigger: PCR-02 (`.planning/phases/08-full-verification/08-CONTEXT-REVIEW.md`) and PLR8-01
  (`.planning/phases/08-full-verification/08-01-PLAN-REVIEW.md`) both flagged that plain
  `uv sync --locked` fails with `invalid peer certificate: UnknownIssuer` in this environment, and
  that Task 2 of `08-01-PLAN.md` will very likely hit this on its first command when executed.
- Machine: this local Windows machine, reproducible from any worktree or clone on it.

## Symptom

```text
$ uv sync --locked
  ├─▶ Failed to fetch: `https://pypi.org/simple/hatchling/`
  ├─▶ Request failed after 3 retries
  ├─▶ error sending request for url (https://pypi.org/simple/hatchling/)
  ├─▶ client error (Connect)
  ╰─▶ invalid peer certificate: UnknownIssuer
```

`uv sync --locked --native-tls` succeeds immediately after. `uv build` succeeds without
`--native-tls` whenever its dependencies are already cached from a prior successful sync, but fails
the same way on a fully cold cache.

## Root cause

**Norton Antivirus's SSL/TLS scanning feature is intercepting this machine's outbound HTTPS traffic,
including uv's connections to PyPI, and `uv`'s default TLS backend does not trust the substitute
certificate Norton presents.**

### Evidence chain

1. **The certificate uv receives for `pypi.org` is not PyPI's real certificate.**

   ```text
   $ openssl s_client -connect pypi.org:443 -servername pypi.org | openssl x509 -noout -issuer -subject
   issuer=OU=generated by Norton Antivirus for SSL/TLS scanning, O=Norton Web/Mail Shield, CN=Norton Web/Mail Shield Root
   subject=CN=pypi.org
   ```

   Norton terminates the real TLS connection and re-signs a substitute certificate for `pypi.org` on
   the fly, using its own locally-generated root CA. This is Norton's "SSL/TLS scanning" traffic
   inspection feature.

2. **That interception is live, not residual configuration.** Confirmed running:

   ```text
   Norton Antivirus       Running
   Norton Firewall        Running
   NortonWscReporter      Running
   nllbIDSAgent            Running
   ```

3. **Norton's root CA is trusted by Windows, but not by uv's default TLS backend.**

   ```text
   Cert:\LocalMachine\Root
   Subject: CN=Norton Web/Mail Shield Root, O=Norton Web/Mail Shield, ...
   NotAfter: 01.01.2040
   ```

   It is installed in the Windows OS trust store, so every OS-integrated HTTPS client (browsers via
   WinHTTP/SChannel, Windows Update, .NET apps) accepts the substitution transparently. `uv`
   defaults to its own vendored TLS stack (Rust's `rustls` + Mozilla's `webpki-roots`), which does
   not consult the OS certificate store. It correctly rejects the substitute certificate as signed by
   an unknown issuer per its own trust policy — hence `UnknownIssuer`.

4. **`--native-tls` changes which trust store uv consults, not the network condition.** That flag
   switches uv to the OS-native backend (SChannel on Windows), which reads `LocalMachine\Root`,
   finds Norton's root already trusted there, and accepts the connection. The interception is
   present in both cases; `--native-tls` makes uv trust the same substitute certificate every other
   OS-integrated tool on this machine already trusts.

5. **Two independent environment variables corroborate the same condition**, both pre-existing
   workarounds for other tools that ship their own CA bundles instead of using the OS store:

   - `NODE_EXTRA_CA_CERTS=C:\ProgramData\Norton\Antivirus\wscert.pem` — Node.js explicitly pointed at
     Norton's certificate file, because Node has the identical "own bundled CA store" problem uv has.
   - `SSLKEYLOGFILE=\\.\nllMonFltProxy\...` — a named-pipe target for TLS session-key logging,
     consistent with Norton's network-filter-driver component (`nllbIDSAgent`) actively intercepting
     the session.

### Why `uv build` sometimes succeeds without `--native-tls`

`uv build` only needs network access if it must resolve or download a dependency (`hatchling`) from
PyPI. If that package is already cached locally from a prior successful `--native-tls` sync, the
build reuses the cache and never opens a new connection to `pypi.org` — so there is no certificate to
validate and no failure. A fully cold cache reproduces the same `UnknownIssuer` failure as `uv sync`.

## Classification

Environmental, specific to this machine's local security software configuration. Not a defect in
the `ggsad` repository, its dependencies, the normative specification, or GSD tooling. Consistent
with the "Baseline condition" already recorded in
`.planning/milestones/PR-3-REBASE-SHA-RECONCILIATION.md` and the Phase 5 evidence, both of which
independently observed and correctly labeled the same failure mode as environmental.

## Reproducibility

- Reproduces identically in any worktree or fresh clone on this machine, since the cause is
  machine-level (Norton's TLS interception plus uv's non-native default trust store), not
  repository- or worktree-specific.
- Would not reproduce on a machine without Norton's SSL/TLS scanning enabled, or on a uv
  configuration that defaults to the native TLS backend (e.g. `UV_NATIVE_TLS=1` set in the
  environment, or `native-tls = true` in a uv config file).
- Does not require code changes, dependency changes, or lockfile changes to resolve — it is a local
  trust-store mismatch, not a supply-chain or packaging problem.
