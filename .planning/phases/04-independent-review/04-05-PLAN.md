Question: Section 8.3 says that `reopen` (full profile) waits when the Definition of Wait of the new corrective scope determines a pause. The table of results in the same section says that `reopen` never answers `blocked`, and Section 22.2 lets only the actions that complete a change or a phase, and `resume`, answer `blocked`, so the result of a paused reopen is not determined. The first approval accepted the drafting choice that `reopen` is never blocked. What does a `reopen` answer when the Definition of Wait of its new scope determines a pause? Options: `Rejected`: nothing is written, `changed` is false and the change stays closed; the request is repeated when the condition is resolved; smallest edit, consistent with the accepted drafting choice and with Section 22.2; the pause itself is not recorded. `Success, then waiting`: the reopen takes effect and answers `success`; the change returns to the resume phase with the status `waiting`; keeps the intent of the earlier wording, Section 22.2 stays as it is, and a successful action can end in a wait. `Blocked`: the evaluation is recorded, the change stays closed and the result is `blocked` with `changed` true, so attempts become countable; Section 22.2, the table of results and the realization row of the result `blocked` then name `reopen`, which changes the accepted drafting choice.

D-2, header `Unevaluable gate`, finding RV-A-003 (MAJOR). Question: Section 24.2 settles `start` when a gate cannot be evaluated: `start` is rejected and no wait is created. What do these actions answer when a gate that applies to them cannot be evaluated? Options: `Rejected`: each of them is rejected with `changed` false, nothing is written and no wait is created, as for `start`; Section 22.2 stays as it is; a cancel or supersede cannot proceed while a failure gate it must evaluate cannot be evaluated. `Cancel proceeds, others rejected`: `cancel` and `supersede` take effect and the `not_evaluable` result is recorded, because a gate that cannot be evaluated is never a failure, while `wait`, `fail` and `reopen` are rejected; an authorized cancellation is never held up, but a hard failure behind a gate that cannot be evaluated is not decided. `Blocked`: the actions answer `blocked`: the evaluation is recorded, the change waits as Section 24.2 says and the requested transition does not occur; Section 22.2, both tables of results and the realization row of the result `blocked` change, and a cancel can leave the change waiting.

D-3, header `Retry limit`, finding RV-B-005 (BLOCKING). Question: The base text lists exceeding retry limits among the conditions that must terminate the flow. The specification makes a retry limit a soft fail condition: when it is reached the change pauses for a human, who closes it as failed or records a bounded override, and a retry limit that declares the severity hard is invalid. This was a drafting choice accepted in the first approval, and no owner decision speaks to it. Which severity may a retry limit have? Options: `Soft, stated openly`: a retry limit stays a soft fail condition as accepted; Section 12, where the obligation to terminate is limited, states that reaching a retry limit pauses the flow for a human disposition and that the flow ends as failed unless a human records an override; wording only, the relaxation of the base text stays, and a reviewer may report it again for the owner's disposition. `Author's choice`: a retry limit declares the severity hard or soft like any other fail condition; reaching a hard retry limit closes the change as failed, a soft one pauses it; the rule that a hard retry limit is invalid is removed and some examples change. `Hard only`: a retry limit is always a hard fail condition as in the base text, reaching it closes the change as failed without human action and no override applies to it, and a retry limit that declares soft is invalid; this reverses the accepted drafting choice and changes several examples.

D-4, header `Text or binary`, finding RV-E-001 (MAJOR). Question: Section 25.2 hashes a text file after line-ending normalisation and a binary file byte for byte, but leaves the decision between text and binary to the implementation and only recommends (SHOULD) that a file is text when its bytes are valid UTF-8 and hold no zero byte. A content hash is therefore comparable only with one computed with the same decision. This was a drafting choice accepted in the first approval. How is the decision made? Options: `One rule that must be followed`: the recommended rule becomes a requirement (MUST): a file is text exactly when its bytes are valid UTF-8 and hold no zero byte, and binary otherwise, so that every conforming implementation computes the same hash for the same bytes; a binary format that happens to be valid UTF-8 without a zero byte is treated as text. `Recorded with the hash`: the implementation keeps its own rule, but every stored content hash of a file is recorded with the kind that was applied (text or binary) and is verified with that kind; larger edit: the definition of the entry of the state document (Section 25.1), the approval and frozen gate records and the examples that show stored hashes change.

D-5, header `Verify-only CI`, finding RV-X-003 (MAJOR). Question: Owner decisions O-2 and O-11 bring continuous integration into scope as verify-only: CI checks history integrity and the anchor, that the frozen gates match the approval, that approvals are current and at the required level, and the scope against the base, and that no hard failure is active, and it does not execute the change's own commands with CI's privileges; CI proves the record, not the outcome. The specification names a read-only action `guard` in Sections 22.1 and 23.4 but never says what it checks, and has no other text for this decision. What should the specification carry?
