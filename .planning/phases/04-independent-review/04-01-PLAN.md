<objective>
Build the first half of the machinery of the independent review before anything is sent anywhere: the read-only check script CHK (stages pins and brief), the neutral review brief BRIEF, the skeleton of the review note NOTE, and a local dry run that sends nothing. Tracer (task 1): the pins of the owner-approved text are read from the note, tied to the owner approval record (through the Phase 3 check) and to the live specification, and scope, status and encoding are enforced, proven end-to-end on a committed skeleton. Task 2 expands: the brief with its pass partition, the snapshot of inputs, the dry run, and the summary. Plan 02 then builds the parser of the reviewer's report and the stage reported.

Purpose: REVIEW-01 asks for findings with stable ids, severity and exact references from a reviewer that is not the Requestor. A review whose inputs are improvised can be anchored without anyone noticing; one whose brief is checked for neutrality, whose inputs are hashed and verified, and whose text is tied to the owner's approval cannot. This plan makes those properties mechanical while nothing has yet left the machine.

Output: CHK (stages pins and brief; helper modes), BRIEF, NOTE (skeleton), a summary.

Why four plans (decided here): the check script, the report parser, the Devin runs and the owner dispositions are separate concerns with different failure modes, and one executor context cannot carry all of them well. Plan 01 is the brief, the inputs and the pins; plan 02 is the parser, reference resolution, findings table and stage reported, verified only on fixtures; plan 03 is the consent checkpoint and the six runs; plan 04 is the owner dispositions and the closing check. Only plan 03 sends anything.

Pass design (decided here, justified): one run cannot be shown to review 4649 lines (about 293 KB, roughly 75 thousand tokens) thoroughly; a model can hold the file, but attention to 3268 inserted lines degrades and nothing in a single output proves coverage. Six runs are planned: RV-A header and sections 1 to 8; RV-B sections 9 to 22; RV-C section 23; RV-D section 24 up to the end of 24.5; RV-E sections 24.6 to 24.10 and section 25 (each of these five covers roughly 700 to 1200 lines and together they partition the whole text by heading, checked by V1); and RV-X, a cross-cutting pass over the whole text for conflicts between distant sections and for tracing every owner decision and requirement to the text that implements it. Every pass is a separate session started from the same brief, and no output of one pass is given to another: cross-feeding would make later passes depend on earlier findings and would have the Requestor carry findings between sessions. Ids are unique per pass and the reports stay separate.

## Standing constraints for this phase (HC-1 to HC-10)

- HC-1 Independence is structural. The only reviewer is Devin CLI run headless (`devin -p`, permission mode `auto`, read-only). No Claude Code subagent, gsd-* agent, fresh context or other Requestor-side agent may perform, supplement, summarise as findings, re-rate, filter, merge or edit any finding. The Requestor (the executing agent) prepares the brief, runs Devin, captures each report verbatim and checks format and fidelity. If Devin is unavailable, fails to authenticate, hits a quota or returns nothing usable, the plan stops at a checkpoint and tells the owner; there is no fallback to another reviewer, a Claude agent or a self-review.
- HC-2 No anchoring. The brief and the inputs carry no conclusion of the Requestor: no drafting-choices register, no advisory review, no unproven-items list, no approval packet, no expected finding, no statement that the text is good beyond the fact of owner approval.
- HC-3 Read-only, no contamination. Devin runs on copies in a throwaway directory outside the repository. After every run: `git status --short` is empty, the specification blob is unchanged, no new file in the repository. Reviewer output files are never committed and never named or linked in committed text.
- HC-4 Consent. Running Devin sends the specification and the decision record to an external service. Plan 03 asks the owner for explicit consent per run set before the first `devin -p` run; no consent or `no reply` means nothing is sent and the phase stays open.
- HC-5 Authority. Only the owner (the human user of the orchestrating session) dispositions a finding: fix, accept with a reason, defer with a reason, or reject with a reason. No agent dispositions, softens, merges or re-rates a finding or defaults the actor or the date; the name and the date are asked, no name is suggested.
- HC-6 Self-contained evidence. The note quotes each reviewer report unedited (mechanical normalisation only), states the pins, the Requestor, the reviewer identity as the reviewer stated it, the severity scale, the findings table and the charter in its own words. It does not link, hash or mention temporary or scratch files, the snapshot directory, reviewer logs, failed or aborted runs, or local absolute paths.
- HC-7 Check script. One lean read-only bash script with stages and seeded failures, shellcheck-clean, LF, UTF-8 without BOM.
- HC-8 If a fix is chosen, the specification edit voids the Phase 3 approval; this phase does not edit the specification; the path is described, not pre-written.
- HC-9 Scope. Only files under .planning/ change. No push, no pull request, no merge, no Phase 5 or later work. REVIEW-01 and REVIEW-02 are ticked only by the orchestrator at phase close, and Phase 4 is not marked complete while a BLOCKING finding lacks a disposition.
- HC-10 Task form: read_first, acceptance criteria with exact commands, concrete identifiers, no fenced code in actions.
