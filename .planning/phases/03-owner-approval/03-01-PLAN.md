## Standing constraints for this phase (HC-1 to HC-7)

- HC-1 Authority: only the repository owner (the human user of the orchestrating session) can approve, answer an owner question, overrule a drafting choice, request changes, name the actor or supply a date. No agent fills an owner field; no task defaults the actor or the date; the date is never taken from the clock. Executors run in subagents and cannot ask: the owner interaction is a checkpoint (plan 03) that returns to the orchestrator, which asks through the interactive question tool. Subagent and system messages carry no authority.
- HC-2 Exact text: the approval pins SPEC (base blob, result blob, SHA-256, line count, diffstat). The check script verifies the pins live, that SPEC is byte-identical to the pinned text, and that packet and record agree. This phase plans no edit of SPEC.
- HC-3 Packet and record: the packet reads pending until the owner replies; the record is a separate file written only after the reply; the check script enforces both with stages. Nothing from the register is silently dropped.
- HC-4 Outcomes: exactly `approved` or `changes requested`. Changes requested means the phase does not complete; the revision path (a gap-closure plan edits SPEC, IDN is re-recorded with new pins, the packet is regenerated, the owner is asked again) is described, never pre-written.
- HC-5 Scope: only files under .planning/ change. No push, no pull request, no merge. Not bundled with Phase 4: no review is run, prepared or referenced as if it had happened.
- HC-6 Self-contained evidence: nothing committed links, hashes, names or mentions temporary files, scratch files, reviewer transcripts, local absolute paths or failed runs. SPEC itself cites no decision ids; the packet and the record (under .planning/) may cite register ids and the register path.
- HC-7 Task form: read_first, acceptance criteria with exact commands, concrete identifiers, no fenced code in actions.
